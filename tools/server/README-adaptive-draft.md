# Adaptive DSpark draft depth

`--spec-adaptive` enables per-request closed-loop depth selection in `llama-server` and the server-based CLI. Every model load first measures costs on the currently loaded target and draft contexts. Costs stay in memory; serving never loads a saved cost file. The default path remains fixed-depth. D is both the actual generated draft count and the verified draft count; the target executes D+1 rows. Shortening D reduces the draft forward itself, including the device sampling uniform vector and probability rows.

## Start

For a Vulkan DSpark configuration with target K/V q4_0/q4_0 and draft K/V f16/f16:

```sh
LLAMA_DSPARK_DEVICE=1 LLAMA_DSPARK_DENSE_Q=1 GGML_VK_DISABLE_COOPMAT=1 \
build/bin/llama-server -m target.gguf -md draft.gguf \
    --device Vulkan0 --device-draft Vulkan0 -ngl 99 -ngld 99 \
    -t 12 -td 12 -np 1 -c 2048 -b 512 -ub 128 -fa on \
    -ctk q4_0 -ctv q4_0 -ctkd f16 -ctvd f16 \
    --spec-type draft-dspark --spec-draft-sampling probabilistic \
    --spec-draft-n-max 7 --spec-draft-n-min 0 --spec-draft-p-min 0 \
    --temp 1 --top-p 0.95 --top-k 0 --min-p 0 --spec-adaptive
```

Use device IDs from `--list-devices`. On Windows, set the environment variables before running the executable. The device path is optional; CPU host sampling also supports startup calibration. `LLAMA_ARG_SPEC_ADAPTIVE=1` is the equivalent startup environment setting. `--no-spec-adaptive` disables the feature. Request parameters cannot supply costs or bypass calibration.

The first implementation requires one sequence, probabilistic anchor-first DSpark, maximum D <= 7, no synthetic acceptance or confidence truncation, partial KV rollback on both contexts, and target/draft ubatch >= maximum+1. Incompatible settings or failed calibration stop startup. Request temperature, top-p/top-k and min-p must match the current load's calibration. D0 disables draft execution and target feature extraction. Context-bucket selection is not implemented.

## Startup measurement

Calibration runs after loading both models and before creating the serving speculator or accepting generation requests. It reuses [the existing calibration API](../dspark-calibrate/README.md) with the current weights, placement, threads, KV formats and sampling settings. Every model reload, including wake from sleep, discards the previous table and measures again. `--no-warmup` does not skip this explicit adaptive calibration.

The server measures D0 through `--spec-draft-n-max`, so a maximum of 7 measures all eight modes. Positive depths use their actual D-row draft forward and D+1-row target verification. There are two warmup rounds and seven timed rounds per depth. D0 is measured first with an ordinary target decode, before enabling feature extraction. A repeated built-in text fills 512 history tokens plus one anchor; smaller context capacities reduce the history to leave room for the largest block. Calibration uses a fixed seed (0 when the serving seed is unspecified) for stable timing. Its acceptance results are never learned as task-wide acceptance observations.

Prefix preparation/restore, sampler reset, warmups, validation and speculator setup are outside the round measurements. The measured round includes draft forward and probability collection, target verification, feature injection, rejection sampling, cleanup, rollback and waits. Server calibration uses the serving pipeline order and allows asynchronous token handoff under the same partial-rollback conditions. Draft collection waits until after target submission; both contexts synchronize at the round boundary. Stage timings are unavailable (zero) in this mode. The standalone calibration tool retains its synchronous phase-timing default. After measurement both KV caches are emptied, temporary speculators are destroyed, and the normal serving speculator starts with fresh sampling state. Each cost uses the median of the seven full-round measurements and 1.4826 times their median absolute deviation (MAD). Log fields `round` and `sd` carry that robust center and scatter, with `statistic=median_mad`. The prediction uncertainty floor remains at least 3%. No cost JSON is read or written.

Startup calibration adds model work before readiness. These fixed-prefix measurements initialize the controller; they do not measure continuous async generation throughput. Runtime observations still update the estimates when context, acceptance and overlap change.

## Feedback loop

Each request starts at min(3, maximum) with fresh acceptance observations, probe state and cooldowns. It does not share learned state across requests. After each real verification, only the observed actual-D row is updated. Accepted positions supply successes and the first rejected position supplies one failure. Unvisited positions receive no label. EOS, stop and output-limit tails are censored: observed successes can be retained without inventing a rejection or treating a partial submission as a normal A+1 reward.

The [shared predictor](../draft-predict/README.md) fits the conditional acceptance model and draws correlated parameter samples to estimate acceptance, throughput and relative gain uncertainty. Observations forget by committed-token age, with a 512-token half-life. Both shorter and longer candidates use the same early-switch rule: the central 90% approximate gain interval must have its lower bound above 3%, with at least eight uncensored rounds at that actual D ending within the last 512 committed tokens. These are model-based intervals, not a coverage guarantee or a measured speedup.

Normal windows contain 16 rounds at one actual D. At their boundary the server drains both contexts, divides complete wall time by the number of rounds, then evaluates a decision. Timing includes forward work, feature handoff, verification, sampling, rollback, waits and host/control work between boundaries. It does not add overlapping asynchronous phase timers. The next window starts at its first draft, after the decision. Work between windows is accounted separately as `boundary_us` and included in total runtime, so short probes do not absorb a larger per-round decision cost. Boundary synchronization waits remain part of each window. A whole window supplies one timing observation, not 16 independent timings. Normal generation does not gain a new synchronization after every round.

For candidate comparisons, boundary work also contributes a shared per-round overhead. The first settled boundary initializes its estimate B; subsequent boundaries update `B += 0.25 * (elapsed - B)`. Every candidate's sampled rate uses `(1 + E[A_D]) / (cycle_time + B/16)`, including candidates currently in eight-round probes. This estimates the candidate's normal operation after promotion. B starts at zero before the first settled boundary and is a shared point estimate, without separate uncertainty or per-depth fitting. Actual probe boundary work remains fully included in total runtime; the amortized estimate is not added again to accounting.

The current load's synchronized measurements supply one weak timing prior per D. Each depth’s measured relative SD, with a 3% floor, defines its own cost-uncertainty parameter rho. Repeated fixed-prefix acceptance results are never imported. Runtime windows update costs and can replace a biased startup estimate. Aging reduces cost evidence weight w but retains weighted population variance V. The relative variance of cost draws is `V / (max(1,w-1) * mean^2) + rho^2 / clamp(w,rho^2,1)`. Once weight drops below one window, even an initially zero-scatter cost loses precision; the aging floor term is capped at 1. Fresh complete windows can narrow the interval again. This is an approximate uncertainty rule. The reported history length identifies the initial measurement; live context growth is handled by forgetting and observed timings, without calibrated context interpolation. Unvisited depths can retain costs measured at a shorter history, so long-context decisions still need validation.

After a normal window, a candidate outside cooldown can start a probe when mean relative gain exceeds 3% and the probability of exceeding 3% is at least 60%. Candidates are ranked by mean relative gain. While the incumbent is positive, if ordinary gain decisions do not qualify, a positive candidate may refresh an unmeasured live cost or one aged at least 128 committed tokens. This requires gain upper bound >3%, probability of >3% gain at least 20%, and expected positive excess gain E[max(gain−3%,0)] >3%. Refresh candidates are ranked by that expectation and respect cooldown and reentry cost. Fresh live costs cannot trigger repeated uncertainty-only probes. No timing credit is required.

A probe episode keeps one candidate and the original incumbent as its comparison baseline. All probes execute eight steady rounds at a time. Each checks for a qualified switch and continues only while the probe conditions still hold. At 16 complete probe rounds, a positive candidate can also switch when mean gain exceeds 3%, probability of exceeding 3% is at least 75%, and both its whole-episode rate and latest-window rate beat the incumbent by 3%. The incumbent measurement must be younger than 512 committed tokens. Rates exclude transitions, include the common B/16 overhead, and charge D0 replay over the remaining horizon. The measured-rate guard also applies to early positive promotions during probes. Otherwise the episode stops at 16 rounds, or earlier when gain is no longer promising. This bounded decision uses a weaker probability threshold than the early-switch rule; it is a policy choice, not a 95% confidence claim. Failed or inconclusive episodes impose a per-candidate cooldown of 128 committed tokens, doubling on repeated failures up to 1024. Cooldown blocks repeat probes and positive-depth switches. A successful switch clears the candidate's failure history and cools the previous incumbent for 128 tokens. The server runs a normal incumbent window before considering another episode after a failed probe. New incumbent measurements may release the D0 switching cooldown, as described below.

Switch qualification uses an integer count of recent normal rounds, separate from the exponentially decayed likelihood weights. Eight recent rounds can qualify even though their decayed weight is below eight; stale and censored rounds cannot qualify. The 2% exploration allowance has been removed. Actual probe duration remains a diagnostic, and neither its time fraction nor the duration of one 16-round episode has a hard time cap. These defaults require real-trace validation and do not guarantee discovering underestimated candidates.

The server clamps D to remaining token/context capacity. Mixed-depth, shortened or terminal windows do not update normal cost estimates. Cancellation drains pending work and closes accounting without fabricating an acceptance observation. A request ending before the first full window may never change its initial D.

## Ordinary fallback and reentry

D0 executes one ordinary target decode, with accepted length exactly zero and reward exactly one. Startup measures D0 before constructing a speculator. Ordinary observations age all existing evidence but add no acceptance or rejection observations to any positive D.

For positive candidates, early switch qualification uses a gain lower bound above 3% plus eight recent uncensored rounds; the 16-round decision described above is a separate qualification path. For D0, prefer ordinary generation when DSpark cannot retain a 3% advantage: use `gain_threshold = -0.03/1.03`, mean gain above that threshold and probability at least 60%. D0 first probes and needs eight recent ordinary rounds before becoming incumbent. This fallback deliberately uses the weaker 60% rule; demanding a 95% gain lower bound would often prevent fallback at equal speed with the 3% cost uncertainty floor. D0 promotion also requires recent measured throughput: both latest valid windows must be younger than 512 tokens and R0_live × 1.03 >= Rd_live. Rates subtract one-time transition costs and add the common B/16 overhead. A posterior-only promotion that fails this guard is rejected. If a newer incumbent window and the existing D0 sample now satisfy both posterior and measured-rate checks, D0 can switch before cooldown expires without another probe.

The controller also checks direct throughput when the posterior holds or schedules any positive-depth probe. The two latest complete normal windows at the current positive depth must both be within 3% of the measured D0 speed or slower. D0 must be at least 5% faster than their pooled tokens per second. A D0 sample up to 64 tokens old can authorize a switch when the remaining output pays for entry, including the cold first forward. At ages 65–511 tokens the sample can authorize an eight-round D0 recheck after cooldown when the projected savings also cover a possible restore. The new steady D0 window must independently satisfy the measured-rate comparison to promote. If the latest positive window alone is at least 5% slower than the measured D0 rate in this comparison, defer weak positive cost refresh and collect another incumbent window. The decision reasons are `ordinary_recent_gain`, `ordinary_recheck`, `ordinary_recheck_gain`, `ordinary_recheck_no_gain` and `ordinary_refresh_deferred`.

If there is no measured D0 window, the controller can measure D0 before a proposed positive-depth probe. The current depth must have slowed by at least 20% from its previous complete same-depth window within 128 committed tokens. D0 must have a predicted mean gain above 3%, a probability of meeting the ordinary fallback threshold of at least 90%, and a mean gain at least five percentage points higher than the proposed probe. This still requires budget for the warmup and eight stable rounds, respects D0 cooldown, and leaves promotion to the usual D0 checks. The log reports `ordinary_probe_priority`. Both priority rules apply to every positive depth.

Entering D0 drains both contexts, saves the target's partial sliding-window state and disables draft feature hooks. Draft KV freezes; only ordinary input token IDs are recorded. Reentry restores the saved target prefix and replays those inputs to fill draft KV, without sampling or emitting extra tokens. A context shift invalidates the resume point and locks this request to D0. Ending a paused request reenables hooks and clears both prompt caches, since their prefixes no longer match.

One-time checkpoint/replay duration is included in runtime and probe time, but subtracted from recurring window cost observations. Reentry comparisons include an estimated restart cost: the number of paused tokens times the latest ordinary round cost, amortized over at most 512 remaining token/context slots. During a restart probe, the estimate is retained and raised to actual replay time if larger. This estimate is a conservative serial-replay heuristic, not a measured bound or a guarantee of profit. It prevents a short remaining request from looking profitable while ignoring restoration. The resident draft model and startup/prefill work remain overheads compared with launching a server without DSpark.

D0 reentry requires fresh evidence: two consecutive complete ordinary windows must show a cost increase above 10% relative to the latest fallback or failed-reentry reference. An isolated slow window resets this count once speed recovers. Cost aging or a wider acceptance interval alone cannot reopen speculation, and uncertainty-only cost refresh is disabled from D0. Once eligible, a new probe requires mean net gain above 3% and probability at least 80%, after replay amortization; old direct rounds cannot bypass this probe. A failed reentry resets the reference and requires a further cost change. D0 does not observe acceptance, so this policy can miss an acceptance-only content change at unchanged ordinary speed. There is no periodic blind probe to recover that information.

`transition_us` reports cumulative transitions, `measured_transition_us` the amount included in the latest window's `round_us`, and `reentry_cost_us` / `gain_horizon_tokens` the latest restart comparison. `cooldown_first_draft=0` identifies the D0-based cooldown array. `ordinary_only` records a context-shift lock.

The first valid live window replaces its startup-prefix cost prior. Subsequent windows use the usual weighted updates. Each depth uses its own calibration relative-SD floor (at least 3%), so one noisy calibration does not widen every candidate.

## Calibration stability and acceptance recovery

When eligible positive-depth probe scores differ by at most two percentage points, choose the candidate with the smaller predicted round cost. This applies both to mean-gain probes and to expected-positive-gain cost refreshes, after their existing probability, gain and cooldown checks. The comparison uses a fixed band from the highest score; it does not chain pairwise ties or prefer a depth number. D0 retains its ordinary-mode priority and transition checks.

After any positive-depth promotion, the first two normal windows contain eight rounds each. Later windows contain 16 rounds; the first suspicious window shortens the next one to eight. Each complete normal window compares its committed tokens per round and measured rate with the promotion's complete probe episode (or the first normal window for the initial incumbent). Two consecutive windows must have reward at most 80% and speed at most 85% of that reference. An isolated dip does not refresh the model. These thresholds and the two-point ranking band are engineering choices, not statistical confidence guarantees.

On a confirmed decline, rebuild only that depth's acceptance counts from its latest 16 uncensored rounds with their original token-age discounts. Keep other depths, costs, token clocks and elapsed/probe time unchanged. Reset the reference to the new regime. Candidates D0 through the configured maximum, including unmeasured depths, must have fresh posterior mean gain above 3% and gain probability at least 60%. An existing window less than 256 tokens old also limits the candidate rate: use the smaller of its measured rate and posterior mean rate. A failed candidate can bypass cooldown only when that fresh measurement exists and its failure predates both new slow windows. The resulting rate must exceed both the two-window pooled current rate and the latest window by 5%. Rank all eligible depths by projected remaining-time savings after an eight-round token budget and estimated D0 entry/possible-restore costs. Old measured speed alone cannot displace a better new posterior plan. Without a viable recovery plan, collect another incumbent window. An already supported direct ordinary fallback keeps its measured decision.

A recovery is an eight-round verification, including a separate charged warmup when entering D0. Both its full steady episode and latest steady window must exceed the new baseline by 5% to promote; otherwise restore the incumbent and cool down the candidate. This new measured verification does not wait for acceptance history from the old regime to establish a 95% lower gain bound. D0 has no draft acceptance and continues to use the existing two-window ordinary-cost reentry rule.

`acceptance_refreshes`, `acceptance_slow_windows`, `acceptance_reference_rate` and `acceptance_reference_reward` expose regression detection. `recovery_probes`, `recovery_switches`, `recovery_probe` and `recovery_baseline_rate` expose verification. `recovery_expected_rate` and `recovery_expected_saving_us` record the selected forecast; per-depth `predicted_rate` records posterior mean speed. Reasons are `acceptance_refreshed`, `acceptance_recovery_probe`, `acceptance_recovery_gain` and `acceptance_recovery_no_gain`. Recovery rules use actual observations and costs at every D; they do not inspect task names or content.

## Observe and test

On a real transition into D0, the first ordinary forward drains in its own warmup window. Its complete duration and transition time remain in runtime/probe accounting, but it does not train steady cost or count toward the 16 steady probe rounds. The next D0 probe measures eight steady rounds before deciding. `measured_warmup=true` and `cost_usable=false` identify the entry window. Terminal or cancelled warmup is still fully charged.

When output/context capacity leaves no room for a positive draft, the server keeps the existing feature hooks. This single-token tail neither creates a D0 resume checkpoint nor replays an already paused draft. It remains timed and censored, without teaching a normal D0 cost.

Each drained decision window logs `adaptive draft: {...}`. `measured_draft`, `measured_rounds`, `round_us` and `cost_usable` describe the completed window. `draft`, `incumbent`, `probe` and `action` describe the next scheduled window. `runtime_us`, `probe_us` and `boundary_us` account actual time, with boundary time settled at the next `begin()` or cancellation. `boundary_mean_us` reports B and `round_overhead_us` reports B/16 used in rate comparisons. `probe_rounds`, `probe_draft`, `probe_episodes`, `probe_outcome` and `switches` describe probe progress and outcomes; `cooldown_tokens` lists remaining cooldowns from D0 through the maximum. `reason` distinguishes gain, cost refresh, fresh D0 evidence, measured-rate rejection and insufficient gain. `predictions` records per-depth costs, gain intervals/probabilities, expected positive excess gain, recent rounds, live-cost window counts, cost age and measured rate. `ordinary_cooldown_releases` counts evidence-driven early D0 switches. `ordinary_reference_rate`, `ordinary_slow_windows` and `reentry_blocked_windows` expose the reentry gate; `probe_tokens` and `probe_elapsed_us` describe the accumulated valid probe episode. `bounded_probe_gain`, `positive_rate_guard` and `ordinary_no_new_evidence` identify the new decisions. Terminal/cancelled requests clear the pending probe state. `rounds` and `windows` count actual feedback received in the current request.

```sh
cmake --build build --target llama-server test-server-component test-speculative-adaptive test-speculative-ordinary
ctest --test-dir build -R '^(test-server-component|test-speculative-adaptive)$' --output-on-failure
```

Tests cover the predictor, drained-window cost updates, actual block lengths, gain-triggered bounded probing, recent-evidence switching, failed-probe cooldown/backoff, phase changes, separated boundary overhead, cancelled probe accounting, terminal limits, request reset and incompatible configurations. Local tiny-GGUF checks exercise real generation and depth changes through the host sampling path, and existing rejection-sampling tests cover dense probability rows at D1/D3/D7. These are functional checks, not performance measurements. End-to-end startup checks use actual tiny-model timings rather than a synthetic cost file. Device DSpark requires GPU-resident Markov weights and cannot run in the local CPU-only build.

An Arc 140T/Vulkan run on 2026-11-19 exercised the device and asynchronous paths with the frozen backend at `9560f2afb`. With Spark 1.7B Q4_K_M target, Q8 draft, K4/V4 target KV, F16 draft KV, 12 threads, target T=1/top-p=0.95 and draft T=1/top-p=1, 84 requests covered test_c, gen.txt and the first five GSM8K problems, seeds 0/1/2 and a 512-token limit. Aggregate decode rates were:

| Input | Fixed D0 | Fixed D3 | Fixed D7 | Adaptive D0-D7 |
| --- | ---: | ---: | ---: | ---: |
| test_c | 35.657 | 34.214 | 20.388 | 34.771 |
| gen.txt | 40.431 | 43.828 | 33.568 | 42.836 |
| GSM8K first five | 42.917 | 67.907 | 71.291 | 66.903 |

Rates are total output tokens minus the first token per request, divided by total decode seconds. Adaptive improved over the preceding controller but still trailed the best fixed depth in each group. Three seeds and capped GSM8K outputs do not establish a general speed or accuracy gain. These results do not validate later backend changes. The feature remains disabled by default.

Model-backed pause/resume validation (supply target and draft GGUF files):

```sh
build/bin/test-speculative-ordinary -m target.gguf -md draft.gguf -t 2 -td 2
```

This compares target logits and resumed draft distributions against continuous feature injection after gaps of 1, 8 and 513 tokens, checks that draft KV freezes, and rejects an invalidated checkpoint. Use device options/environment to exercise the device path; CPU success alone does not validate Vulkan asynchronous handoff.
